THE SYMPTOM

Your agent is inconsistent.

You've swapped models back and forth. Added more instructions. Added more skills, more tools. The results stay inconsistent — sometimes brilliant, sometimes mediocre.

Every new model release generates the same hopeful thought:

“This one will fix my workflow!”

After burning millions of tokens: things improved. It's not fixed. It's more expensive though.

THE CLAIM

Almost every quality problem in AI agents traces back to poor context decisions — not model capability.

If that resonates, you don't have a model problem. You have a context problem.

ACT I · THE CONTEXT WINDOW · 01

There is no conversation. There's an HTTP request.

The model has no memory between calls. Everything it knows comes from what's in the payload right now — the context window. It holds four things:

SYSTEM

System prompt

Instructions defining the agent's role, behavior, and rules.

TOOLS

Tool definitions

Descriptions of every tool the agent can call — params and return shape included.

HISTORY

Conversation history

Every prior user message and assistant response in the current session.

INJECTED

Injected knowledge

Search results, file contents, retrieved memories and skills — anything added dynamically.

ACT I · THE CONTEXT WINDOW · 02

Every turn, the whole thing goes over the wire

Every turn sends the full context window to the provider — cloud or local.

ACT I · THE CONTEXT WINDOW · 03

A bigger context window doesn't mean it's free to fill

  • Every token included costs money.
  • Every token included is a token the model must attend to.

So what does "attends to" actually mean?

ACT II · ATTENTION & THE KV-CACHE · 04

Attention scores every pair of tokens

For each token, the model computes a score against every other token in the context — how much each one should influence the next token generated.

Completing "Caracas is the capital of", the model attends more strongly to "capital" and "Caracas" than to "is" and "the." The scores reflect relevance.

1,000 tokens → 1,000,000 pairs to score. Double the context to 2,000 and it's 4,000,000 pairs. Four times the compute for twice the tokens.

Attention is quadratic in context length.

ACT II · ATTENTION & THE KV-CACHE · 05

Quadratic, not linear

Doubling context length quadruples the number of attention pairs the model must score.

ACT II · ATTENTION & THE KV-CACHE · 06

The second cost: relevance degrades

The model doesn't skip tokens that aren't relevant. They're there, and they still affect the quality of the result.

If half the context is boilerplate that doesn't apply to this specific task, those tokens still compete with the ones that do.

It costs us more money and it compromises quality.

ACT II · ATTENTION & THE KV-CACHE · 07

Where those scores live: the KV-cache

Each arrow carries the cached key/value pair of the target token. "The" is looked up three times — its stored pair is reused, never recomputed.

Double the context length, quadruple the KV-cache memory.

ACT II · ATTENTION & THE KV-CACHE · 08

Why the model "feels dumber" in long sessions

GPU memory is one of the most contested resources on the planet. DRAM prices roughly tripled by late 2025 as producers shift capacity toward AI. KV-cache memory is one of the largest costs for cloud providers.

At very long context lengths, providers fall back to compressed context representations to keep serving requests. Compression is usually lossy — pushed aggressively, output quality degrades.

It's not your imagination, and it's probably not the model. The model is the same. The context isn't.

An agent that runs long sessions without managing its context doesn't just get expensive. It gets unreliable.

ACT III · THE PREFIX CACHE · 09

Not all tokens are equally expensive

Providers cache the KV-cache of each request for a limited time. If the beginning of your next request is identical to the previous one — everything the same except the last message — the provider reuses the cached KV-cache and only computes the new tokens.

As long as the cached prefix hasn't expired, you pay to compute it once, then reuse it across every subsequent turn for a fraction of the cost.

NOTE

Local models get this too. There the "payment" is waiting for the whole conversation's KV-cache to be computed before the response starts — the hardware is just slower than a provider's.

ACT III · THE PREFIX CACHE · 10

One matching prefix = pay once, reuse every turn

A matching conversation prefix is a cache hit. Only the new tokens need to be computed.

ACT III · THE PREFIX CACHE · 11

What an invalidated cache actually costs you

  • The whole prefix gets recomputed — you pay full price for every token, not just the new ones.
  • Time-to-first-token jumps back to the cold-start number. Every turn feels like the first turn.
  • If something in the prefix changes on every turn — a timestamp, a reordered tool list, a reshuffled system prompt — the cache never builds at all. Every single turn pays the uncached price, and that price keeps growing as the conversation grows.

A cache that never hits isn't just slower. It's the expensive path — on every single turn.

ACT III · THE PREFIX CACHE · 12

Two rules that follow directly

  1. Use a reasonable prefix-cache expiration time.
  2. Never inject dynamic content into the system prompt of an active conversation — no Current date: <date> at the top.

Keep static instructions in the system prompt. Put dynamic state in the conversation messages.

ACT IV · SPECIALIST TEAMS · 13

The generalist trap

A broad system prompt feels productive. Cover every case, add 30 tools, the agent can "do anything." Then it does everything... average. Same problem: irrelevant instructions and tool definitions are still read, and still scored, on every turn.

A specialist agent with a 100-token system prompt and 2 relevant tools consistently outperforms a generalist with a 100,000-token prompt and 10 tools — on the tasks the specialist is built for.

Context length alone degrades performance 13–85%, even with perfect retrieval. — arXiv:2510.05381

ACT IV · SPECIALIST TEAMS · 15

The fix isn't a smarter agent. It's several smaller ones.

An orchestrator that reasons about the task, breaks it down, and delegates. Workers that execute each step with minimal, focused context.

The planner coordinates steps. Developer and reviewer talk directly. The orchestrator only sees the result.

ACT IV · SPECIALIST TEAMS · 16

Two things define a role: system prompt + tool list

A developer without delegation tools simply cannot delegate — not because it's told not to. The capability isn't there.

We can't prompt our way out of a missing tool.

01

Stable system prompts

Each agent's prompt doesn't grow as other agents gain capabilities. The prefix cache actually works — pay to compute it once, reuse it every turn.

02

Higher quality per step

A worker that only knows how to search is very good at searching. Narrow scope produces better outputs, not worse.

ACT V · THE 20/80 SPLIT · 17

We fixed context. Now look at the bill.

Teams of specialists work. Quality is good. But it's getting expensive fast. The instinct is to drop to a cheaper frontier model at the cost of quality. Wrong move.

The question isn't which frontier model to use. It's: which steps actually need one? Most of them don't.

ACT V · THE 20/80 SPLIT · 18

Frontier models are exceptional at one thing: turning ambiguous intent into a precise spec

"Clean up the auth module" is underspecified — it takes judgment to get to a real plan. Once the spec is precise, execution is mostly mechanical.

The expensive part of a workflow is knowing what to do. Doing it is mostly mechanical.

The orchestrator runs once to reason and specify. Workers run constantly to execute. Cost follows the split.

ACT V · THE 20/80 SPLIT · 19

The model didn't get smarter. The input did.

The same model produces mediocre results on a vague ask, and reliably handles a precise one.

Ambiguous

"Refactor the auth module."

Needs brainstorming, follow-up questions, and judgment. Even a strong model guesses at scope.

Precise spec

"Extract the session handling from user_controller.ex into a new Session module, preserving the existing public interface."

A small, cheap, local model follows this almost flawlessly.

ACT V · THE 20/80 SPLIT · 20

Cost isn't the only reason to route to local

  • Data stays on your own hardware — code, context, history never leaves.
  • Pricing is predictable; electricity is the main cost.
  • Models don't change under you unless you update them.
  • Throughput is bounded by your machine, not a provider's queue.

Frontier for thinking. Local for doing.

ACT VI · TAKEAWAYS

What to change this week

01

Audit one system prompt

How much of it applies to the task the agent is actually doing right now?

02

Kill dynamic system prompts

Move dates and live state out of the system prompt and into the messages, so the prefix cache can do its job.

03

Split one generalist agent

Turn one "does everything" agent into an orchestrator plus one or two narrow workers.

04

Separate spec from execution

For one workflow, route "deciding what to do" and "doing it" to the model each actually needs.

DISCUSSION

Bring one example

Pick an agent or prompt you maintain. Answer, out loud, for the group:

  • What's actually in its context window right now — system prompt, tools, history, injected knowledge?
  • What in there is dead weight on a typical turn?
  • Is anything dynamic sitting in the system prompt where it can break the prefix cache?

The model wasn't the problem. It never was.
